# FTDX10 固件逆向：完整可复现分析过程

> 本文记录**每一个结论是怎么得来的**，含工具、命令、判据、原始输出。
> 目标：任何人在同一份固件上按本文操作，都能独立复算出同样的结论。
> 结论汇总见 `短接点功能说明.md`（短接点）与 `../power/功率解锁方案.md`（功率修改）。
> MAIN 固件代码地址 = **文件偏移**（`decoded/firmware/FTDX10_MAIN_V0115.bin`，259,668 字节）；RAM/外设寄存器地址按运行时地址标注；DISPLAY 的运行时地址在 §8 单独说明。

* 想复核结论 → 直接跳到对应步骤，粘贴命令即可。

## 2. 步骤 0：数据来源与解码

**目的**：得到可分析明文（S-record 文本 + 连续二进制）。

`.SFL` 结构：`[0..575]` 576 字节文本标头 + 其后混淆数据段；
混淆 = 逐字节减去 43 字节固定密钥（密钥是 1..43 的一个置换）。

```bash
cd $ROOT
python3 decoded/yaesu_sfl_tool.py decode original/firmware/FTDX10_MAIN_V0115.SFL -o decoded/firmware
```

**判据**：解出的 `decoded/firmware/FTDX10_MAIN_V0115.srec` 每条 S-record 校验和合法，
且 `decoded/firmware/FTDX10_MAIN_V0115.bin` = 259,668 字节（= `0x3F654`）。

```bash
ls -l decoded/firmware/FTDX10_MAIN_V0115.{bin,srec}
# -rw... 259668 ... FTDX10_MAIN_V0115.bin
# -rw... 738410 ... FTDX10_MAIN_V0115.srec
```

**验证解码正确（独立法）**：用 `yaesu_sfl_tool.py verify` 做“解码→回打包”SHA-256 比对；
也可用 `decoded/verify/roundtrip_test.py` 做独立的逐字节回环。

```bash
python3 decoded/yaesu_sfl_tool.py verify original/firmware/FTDX10_MAIN_V0115.SFL
# → OK ... SHA-256(原始 = 重建)
python3 decoded/verify/roundtrip_test.py                      # 独立回环（可选）
```

## 3. 步骤 1：建立反汇编

```bash
OBJ=hardware/files/tools/objdump
$OBJ -D -b srec -m h8300sx --adjust-vma=0 \
     $ROOT/decoded/firmware/FTDX10_MAIN_V0115.srec > hardware/files/disasm/main_disasm.txt
```

**注意**：归档的 `main_disasm.txt` 是 S-record 渲染（节名 `.sec1`）；不同 binutils
版本/区域设置可能只改变文件头和地址宽度，指令流应一致。若要从 `.bin` 生成另一种
渲染，输出到 `main.asm`，不要覆盖主力反汇编。

`objdump` 会把 >4 字节的指令拆成"续行"。
`h8.py` 的职责就是把这些续行重新拼成完整指令，因此检索**必须用 `h8.py`**，
不能直接 `grep`（会漏匹配或误匹配）。

```bash
python3 hardware/files/scripts/h8.py show 0xa76 0xa8e     # 显示某区间
python3 hardware/files/scripts/h8.py find "0xfffba3"       # 全镜像检索
python3 hardware/files/scripts/h8.py ctx 0x7d2e 0 0        # 单点上下文
```

## 4. 步骤 2：短接点到底有没有被读取（决定性步骤）

> 用户要求："不要只 grep，可能是同类不同名称的方案读取。" ⇒ 下面用**三种互相独立的判据**。

### 4.1 全镜像读 `PORTK(0xFFFBA3)` 的指令只有 4 条

```bash
python3 hardware/files/scripts/h8.py find "0xfffba3"
```

实跑输出：

```
     a8a:  6a 29 00 ff fb a3      mov.b	@0xfffba3:32,r1l
     ac8:  6a 30 00 ff fb a3 73 70 btst	#0x7,@0xfffba3:32
     ae4:  6a 30 00 ff fb a3 73 70 btst	#0x7,@0xfffba3:32
   17364:  6a 28 00 ff fb a3      mov.b	@0xfffba3:32,r0l
  [4 shown]
```

逐条归属：

| 地址 | 指令 | 例程 | 读到 | 可达性 |
|---|---|---|---|---|
| `0xA8A` | `mov.b @0xfffba3,r1l` | `0xA76`（列 4 = KSC） | 全 8 位 | 只被 `0xA60` 调；`0xA60` 只被 `0xA26`/`0xA38` 调 |
| `0xAC8` | `btst #7,@0xfffba3` | `0xA92`（列 0） | 仅 KR7 | 被 `0x830` 调（面板键） |
| `0xAE4` | `btst #7,@0xfffba3` | `0xA92`（列 1） | 仅 KR7 | 同上 |
| `0x17364` | `mov.b @0xfffba3,r0l` | `0x17358`（扫描列 0–3） | 全 8 位 | 被 `0x139C`/`0x171C8` 调（面板矩阵） |

**关键判别**：只有 `0xA8A` 是在**配置列（列 4 = KSC）**上读的；
`0x17364` 的扫描器**只循环列 0–3**（`0x1737E: 列号++ ; 若列号 != 4 → 0x173F6`），
`0xA92` 只 `btst #7`。列选通写 `PCDR` 的全镜像只有两处（`0x12E6` 初始化写 0、`0x173F6` 内部）。

```bash
python3 hardware/files/scripts/h8.py show 0x173f6 0x1740e   # 列选通
python3 hardware/files/scripts/h8.py show 0x17358 0x17390   # 扫描器循环边界
```

### 4.2 `0xA26` 是死代码：三种独立扫描（`0xA58` 不是独立入口）

调用链：`0xA26 ← 0x7E9E ← 0x7E8E ← 0x7D2E`。

```bash
# 扫描 A：反汇编文本中带 0x 前缀的 0x7d2e 引用
grep -ci "0x7d2e" hardware/files/disasm/main_disasm.txt      # → 0

# 扫描 B：二进制中 32 位长字 00 00 7D 2E（跳转表项）的次数
python3 -c "
d=open('$ROOT/decoded/firmware/FTDX10_MAIN_V0115.bin','rb').read()
print(d.count(bytes.fromhex('00007d2e')))"          # → 0

# 扫描 C（含 A/B、阳性对照、A26/A38/A58 活路径断言；唯一 Python 实现）
python3 verify/verify_short_jumper.py
# → text=0x0 long4=0x0 long3=0x0 branch=0
# → ==== PASS: 16/16 checks passed ====
```

**阳性对照**（只说明“跳转表长字引用”这一项）：活的菜单处理例程
`0x15920`、`0x20DB4`、`0x20D80` 虽无 `jsr @imm` 调用者，但在跳转表里**各有 1 处长字引用**：

```bash
python3 -c "
d=open('$ROOT/decoded/firmware/FTDX10_MAIN_V0115.bin','rb').read()
for a in (0x15920,0x20db4,0x20d80,0x7d2e):
    print(hex(a), d.count(a.to_bytes(4,'big')))"
# 0x15920 1 / 0x20db4 1 / 0x20d80 1 / 0x7d2e 0
```

`0xA26` 本身有 `0x7E9E` 的直接 `jsr`，它之所以是死代码，是因为唯一入口
`0x7D2E` 无引用；长字引用=0 只是辅助证据，不是通用判据。`0xA58` **不是函数入口**，
而是活函数 `0xA38` 的尾部写回（`0x1570 → 0x8E50 → 0x8E54 → 0xA38 → … → 0xA58`）。它确实会执行，
但只写回 `A38` 已掩码的结果；跳线的 bit3/bit4 仍未进入配置字节。

⇒ **`0xA26` 是死代码；`0xA58` 属于活路径，不能称为死代码。**

### 4.3 唯一活路径 `0xA38` 只刷新 bit5（EXP）

```bash
python3 hardware/files/scripts/h8.py show 0xa38 0xa60
```

实跑（节选）：

```
     a38:  5e 00 0a 60      jsr	@0xa60:24      ; 读配置列 → r1
     a42:  6a 28 00 ff 20 07 mov.b	@0xff2007:32,r0l
     a48:  79 60 ff 9f      and.w	#0xff9f,r0     ; 清 bit5、bit6
     a4c:  79 61 00 20      and.w	#0x20,r1       ; 只留跳线 bit5
     a50:  64 01            or.w	r0,r1
     a58:  6a a9 00 ff 20 07 mov.b	r1l,@0xff2007:32
```

⇒ `0xA38` **不采用跳线输入的 bit3/bit4**（保留 `0xFF2007` 原有 bit3/bit4），只把 bit5（EXP）换成跳线状态，并清 bit6（AUX0）。

**结论**：`PORTK` 的配置列只被 `0xA8A` 读；其唯一活消费者 `0xA38` 丢掉 PWR 位。
⇒ **跳线短接与否不影响功率档位。**

### 4.4 等价载体排查（防"同类不同名"）

| 假设的替代读法 | 检索 | 结果 |
|---|---|---|
| 读 `0xFF2006`（FRAM[6]）当配置 | `find "0xff2006"` | 有引用，但**从不掩 bit3/4**，无行为 |
| 读一个字（会同时含 bit3/4） | `find "mov\.w\s+@0xff2006"` | **0 处** ⇒ 无"字读污染" |
| 读拆分缓存 `0xFF98C7/8` | 见 §6 | 缓存本身源自 `0xFF2007`，非独立来源 |
| 配置镜像 `0xFFABD0`（↔ FRAM `0x414`） | `find "0xffabd0"` | 2 处**写**（`0x195E2`/`0x19636`：`r0l=@0xFF2007; @0xFFABD0=r0l; r1=0x414; jsr 0xA528`），逐字节复制，不掩位 |
| 读 `0xFFAB2B` 的 2 位字段 | 见 §6.2 | 是**菜单设置打包字节**，不在功率链上 |

## 5. 步骤 3：功率档读取点全集（把 `and.b #0x18` 一网打尽）

**判据**：名为 PWR 的字段是 2 位（bit3=PWR0、bit4=PWR1），固件里"取这 2 位"必然写成
`and.b #0x18,Rn`。所以先抓**全镜像所有 `and.b #0x18`**，再逐个用上下文判定它读的是不是配置字节。

```bash
python3 hardware/files/scripts/h8.py find "and\.b\s+#0x18" 9999
```

实跑输出（共 **12** 处）：

```
    150c:  e0 18   and.b	#0x18,r0h     ← 0xFF2007
    1544:  e0 18   and.b	#0x18,r0h     ← 0xFF2007
    8112:  e8 18   and.b	#0x18,r0l     ← 0xFF2007
   12e18:  e8 18   and.b	#0x18,r0l     ← 0xFFAB2B
   1595c:  e0 18   and.b	#0x18,r0h     ← 0xFF2007
   159d4:  e0 18   and.b	#0x18,r0h     ← 0xFF2007
   20548:  e8 18   and.b	#0x18,r0l     ← *er1
   2055c:  e8 18   and.b	#0x18,r0l     ← *er1
   2cb2a:  e0 18   and.b	#0x18,r0h     ← 0xFFAB2B
   38a5e:  e0 18   and.b	#0x18,r0h     ← 0xFFAB2B
   3bb8a:  ee 18   and.b	#0x18,r6l     ← 0xFF2007
   3bca6:  ea 18   and.b	#0x18,r2l     ← 0xFF2007
```

> 计数口径：这里的 **12 处**指**按指令边界线性反汇编**的命中数（正确口径），

> 的伪命中（`0x2427E/0x2467E/0x2487E/0x28B44/0x3BAAB`），共 17 对；
> 它们都落在别的指令/数据中间，不是真正的 `and.b #0x18`。复核时请以反汇编为准。

### 5.1 七处功率相关（输入 = 配置字节 `0xFF2007`）

用 `ctx` 看各处与 `mov.b @0xff2007,...` 的距离：`0x8112`/`0x1595C`/`0x159D4`/`0x3BB8A`/`0x3BCA6` 的前一条就是该读取；`0x150C`/`0x1544` 的读取在 4 字节前的 `0x1502`/`0x153A`（中间隔 `mov.b r0l,r0h`、`and.b #0x7,r0l` 两条）：

```bash
for a in 150c 1544 8112 1595c 159d4 3bb8a 3bca6; do python3 hardware/files/scripts/h8.py ctx 0x$a 2 1; done
```

| # | 地址 | 所在例程 | 语义 | 对功率修改 |
|---|---|---|---|---|
| 1 | `0x150C` | `0x1502` | 开机拆分：PWR→`0xFF98C8`，置 `0xFF204A.7` | 不直接改上限 |
| 2 | `0x1544` | `0x153A` | 同上（另一分支） | 不直接改上限 |
| 3 | `0x8112` | `0x810C` | FRAM 默认初始化按档写 F/AC | 加固项 |
| 4 | `0x1595C` | `0x1594C` | **RF POWER 菜单区间取档** | **必需** |
| 5 | `0x159D4` | `0x159CC` | **MAX POWER 菜单区间取档** | **必需** |
| 6 | `0x3BB8A` | `0x3BB6E` | 20W 档把 HF 硬限到 10W | 20W/10W 机需要 |
| 7 | `0x3BCA6` | `0x3BCA0` | **功率等级钳位取档** | **必需** |

### 5.2 排除"第二条读取路径"（穷尽性判据）

```bash
python3 hardware/files/scripts/h8.py find "cmp\.b\s+#.*,@0xff2007" 9999   # [0 shown]
python3 hardware/files/scripts/h8.py find "btst\s+#0x[34],@0xff2007" 9999 # [0 shown]
```

即除上表 7 处 `and.b #0x18` 外，**没有任何** `cmp.b #imm,@0xFF2007` 或
`btst #3/#4,@0xFF2007` 形式的第二位读取者。

### 5.3 与 `0xFF2007` 相关的其余指令（分类）

```bash
python3 hardware/files/scripts/h8.py find "0xff2007" 9999        # 46 shown
python3 hardware/files/scripts/h8.py find ",@0xff2007" 9999      # 写者 6 + btst#5 1
python3 hardware/files/scripts/h8.py find "mov\.b\s+@0xff2007" 9999   # 读者 39
```

* **写者 6 处**：`0xA30`（死路径 `0xA26`）、`0xA58`（活路径 `0xA38`，只写 bit5）、`0x7D22`、`0x7D3E`、`0xDC66`、`0x27F68`。
* **EXP 唯一位测试 1 处**：`0x32B06 btst #0x5,@0xff2007`。
* **其余**：`and.b #0x7`（TS 三位）、整字节搬运、ASCII 帧收发、状态/遥测（无功率行为）。

> 完整、无遗漏的 **39 处读者分类表**见 §5.4（其中**没有一处掩 bit6/bit7**）。


### 5.4 读 `0xFF2007` 的 39 个读者全表（穷尽性复核）

把"`0xFF2007` 读进寄存器"的**全部 39 处**列出，并标出紧随其后的动作——
**没有任何一处掩 bit6 或 bit7**（⇒ AUX0/AUX1 在 MAIN 中确无消费者）。

| 角色 | 读入点（39 处中对应的起点） | 数量 |
|---|---|---|
| **PWR 档**（随后 `and.b #0x18`） | `0x1502`、`0x153A`、`0x810C`、`0x15956`、`0x159CE`、`0x3BB84`、`0x3BCA0` | **7** |
| TS 位（随后 `and.b #0x7`） | `0x0B16`、`0x8094`、`0x80A0`、`0x80AC`、`0x8522`、`0x8730`、`0x87BC`、`0x9F58`、`0xAF04`、`0xEDCC`、`0x156F8`、`0x15746`、`0x16FA4`、`0x1AA52`、`0x1BE56`、`0x32B10` | 16 |
| EXP 位（bit5） | `0x0A42`（`and.w #0xFF9F` + `and.w #0x20`）、`0x27F5C`（`and.b #0x20`） | 2 |
| ASCII 状态帧（收发） | `0x2D820`、`0x2D87A`、`0x2D930`、`0x2D994` | 4 |
| 配置字节镜像 / FRAM 写 | `0x8F2C`、`0x195E2`、`0x19636` | 3 |
| 配置字节重组 | `0xDC4C`（`and.b #0xF8`+`and.b #0xE7`+OR 缓存） | 1 |
| 其它（工厂记录 / 显示解码 / 低 5 位值域） | `0x08AE`、`0x21888`、`0x27FAC`、`0x27FC0`、`0x27FFC`、`0x28012` | 6 |
| **合计** | | **39** |

> 与 §5.1 的对应：7 处 `and.b #0x18` 的"读入点"就是上表第一行
> （`0x150C`/`0x1544` 属于 `0x1502`/`0x153A` 例程内，读入点记为 `0x1502`/`0x153A`；
> `0x8112`→`0x810C`、`0x1595C`→`0x15956`、`0x159D4`→`0x159CE`、`0x3BB8A`→`0x3BB84`、`0x3BCA6`→`0x3BCA0`）。
> 复现：`§9` 脚本第 2 段；或 `python3 hardware/files/scripts/h8.py find "mov\.b\s+@0xff2007" 9999` 后逐条看后继指令。

### 5.5 `0x20548/0x2055C` 是什么

`ctx` 显示它们读 `@er1`（指针），并对 `0xE7`/`0x18` 做掩码、按 ±8 步进后写回：
这是**设置菜单里某个 2 位枚举项的 ±1 步进器**（同族还有 `0x204F8` 设 `er1=0xFFABBD` 后掩 `0xCF/0x30`）。
不在功率链上。

## 6. 步骤 4：功率模型全链（50W 的两个软件闸门）

### 6.1 档位 → 菜单区间表 `0x159F6`

```bash
python3 -c "
d=open('$ROOT/decoded/firmware/FTDX10_MAIN_V0115.bin','rb').read()
print(d[0x159f6:0x159f6+32].hex(' '))"
# 05 64 05 32 05 0a 05 0a  05 64 05 32 05 14 05 0a
# 05 32 05 32 05 14 05 0a  05 19 05 19 05 14 05 0a
```

按"组(4)×档(4)"解成 `(min,max)`（`0x64`=100、`0x32`=50、`0x19`=25、`0x14`=20、`0x0a`=10）：

| 组 | 含义 | 档0=`0x18` | 档1=`0x00` | 档2=`0x08` | 档3=其它 |
|---|---|---|---|---|---|
| 0 | HF | (5,**100**) | (5,50) | (5,10) | (5,10) |
| 1 | 50M | (5,**100**) | (5,50) | (5,20) | (5,10) |
| 2 | 70M | (5,50) | (5,50) | (5,20) | (5,10) |
| 3 | AM | (5,25) | (5,25) | (5,20) | (5,10) |

索引函数 `0x1594C`（RF POWER）/`0x159CC`（MAX POWER）：`0x18→0`、`0x00→1`、`0x08→2`、其它`→3`；再按频段组加 `0/4/8/12` 后 ×2。

```bash
python3 hardware/files/scripts/h8.py show 0x1594c 0x15970
```

### 6.2 有效上限 `0x3BBC6 = min(F, AC)`

> F（`0x335–0x338`）是 **RF POWER**（发射功率设定），AC（`0x46A–0x46D`）是
> **MAX POWER**（各频段上限）；两者都是每频段用户可改的值，有效值取较小者。

```bash
python3 hardware/files/scripts/h8.py show 0x3bbc6 0x3bbf0
```

```
3bbc6: btst #0x7,@0xff2020 ; bne 0x3bbe2     ; 服务模式 → 直接给值
3bbd0: jsr @0x3bb3a        ; er1 = &F[子波段]
3bbd4: mov.b @er1,r1l      ; F
3bbd8: jsr @0x3bb6e        ; r0l = min(r0l, AC[子波段])
3bbde: mov.b r1l,r0l ; rts
```

* `F = 0xFFAAF1–F4 ↔ FRAM 0x0335–0338`（HF/50M/70M/AM）
* `AC = 0xFFAC26–29 ↔ FRAM 0x046A–046D`

### 6.3 等级钳位 `0x3BCA0`

```bash
python3 hardware/files/scripts/h8.py show 0x3bca0 0x3bce8
```

`0x3BCA6` 取档 → `0x18` 不钳；`0x00`→≤4；`0x08`→≤3（子带 <9 时 ≤2，子带 ≥9 时 ≤3）；其它→≤2。

### 6.4 FRAM 默认块与初始化链

## 7. 步骤 5：EXP 位分析

```bash
python3 hardware/files/scripts/h8.py show 0x32aee 0x32b30
```

* 选择器优先级：**服务模式（`0xFF2020.7`）＞ EXP（`0xFF2007.5`）＞ 按 TS**。
* `0x32B06 btst #0x5,@0xff2007` 是**全固件唯一**消费 EXP 的位测试。
* 三张表：`0x32B4A`（服务，1 段 1.8–75）、`0x32B54`（EXP，3 段 1.8–30/50–54/70–70.5）、
  `0x32B2A`（按 TS 的 8 项长字指针表）。

```bash
python3 hardware/files/scripts/h8.py find "btst\s+#0x5,@0xff2007" 9999   # 1 shown
python3 hardware/files/scripts/h8.py find "and\.b\s+#0x20,r0l" 9999      # 1 shown (0x27f62)
```

⇒ EXP 的**全部消费点只有 2 处**（`0x32B06`、`0x27F62`）。
`0xA38` 会覆盖 bit5 ⇒ 想开 EXP 用硬件短接 JP1006 最稳（详见 `../power/功率解锁方案.md` §3.4）。

### 7.1 TS 表逐段解析（补充）

`0x32B2A` 的 8 个长字指针指向 `0x32B6E…`，每张表是 `u16 count + count×(u32 start, u32 end)`。
直接按二进制展开（单位 MHz；`end` 已按“上限-1”折算）：

| TS | 指针 | 段 | 覆盖 |
|---:|---|---:|---|
| 0/1/5/6 | `0x32B6E/0x32BC0/0x32D7A/0x32DCC` | 10 | 1.8–2 / 3.5–4 / 7–7.3 / 10.1–10.15 / 14–14.35 / 18.068–18.168 / 21–21.45 / 24.89–24.99 / 28–29.7 / 50–54 |
| **2** | `0x32C12` | 12 | 1.81–2 / 3.5–3.8 / **5.25–5.4065** / 7–7.2 / … / 28–29.7 / 50–52 / **70–70.5** |
| **3** | `0x32C74` | 11 | 1.8–2 / 3.5–3.8 / **5.3515–5.3665** / 7–7.2 / … / 50–52 |
| 4 | `0x32D28` | 10 | 1.83–1.85 / 3.5–3.8 / 7–7.1 / … / 50–52 |
| **7** | `0x32CCE` | 11 | 1.8–2 / 3.5–4 / **5.3515–5.3665** / 7–7.5 / 10–10.5 / 14–14.5 / 18–18.5 / 21–21.5 / 24.5–25 / 28–30 / 50–54 |

## 8. 步骤 6：升级逻辑归属与保底恢复（DISPLAY 侧）

```bash
# 注意：归档的 hardware/files/tools/objdump 只编译了 h8300sx 目标，不能 -m arm；
# DISPLAY 是 ARM，请用系统 objdump（若支持 ARM），或改用 capstone：
python3 -c "from capstone import *; d=open('$ROOT/decoded/firmware/FTDX10_DISPLAY_V0106.bin','rb').read(); \
md=Cs(CS_ARCH_ARM,CS_MODE_ARM); \
[print(hex(0x20100000+i.address), i.mnemonic, i.op_str) for i in md.disasm(d[0x14c40:0x14ca0],0x20114c40)]"
# 或：objdump -D -b binary -m arm --adjust-vma=0x20100000 \
#        $ROOT/decoded/firmware/FTDX10_DISPLAY_V0106.bin > hardware/files/disasm/display_disasm.txt
# （生成缓存的 display_disasm.txt 时未加 --adjust-vma，文件内地址=文件偏移，用它检索时需 +0x20100000）
```

* **可见 MAIN 镜像中无升级逻辑**：无 SFL/BOOT/LOADER 字样（有 `FIRMWARE UPDATE` 菜单文本、`SD CARD` 提示文本，但只是 UI 文案）、0 处 `FKEY/FMATS` 写（`#0xA5/#0x5A/#0xAA` 在镜像里有 25 处，但目标都是普通寄存器/FRAM，不是 flash 解锁序列）、
  0 处 flash 控制寄存器（FCCS `H'FFDE8`/FKEY `H'FFDEC`/FMATS `H'FFDED`，即 `0xFFFDE8–0xFFFDEE`）访问 ⇒ MAIN 不能自编程，是被 DISPLAY 写入的。
* **DISPLAY 基址** = 文件偏移 + `0x20100000`（由 27 条启动串中 18 条的字面量对齐 + SP 字面量 `0x2044C000` 落在 FLASH 末端 `0x204379DC` 之后共同印证）。
* **Boot loader**：字符串在文件 `0x32CBE4–0x32D26C`
  （`YAESU FTDX10 BOOT LOADER V01-00`、`FIRMWARE BOOT ERROR`、`MAIN/DISPLAY FIRMWARE UPDATE`…）。
* **SFL 校验**：CRC-16 表生成 @`0x9B0`（poly `0xA001`）；CRC-32 表生成 @`0xA34`
  （poly `0xEDB88320`，字面量 @`0xAB4`）；`crc32_update` @`0xA7C`；`mvn r0,r0` @`0xAA8`（zlib 风格）；
  整文件 CRC 校验循环 @`0x14C60–0x14C94`；43 字节密钥 @`0x32D420`。

```bash
python3 -c "
d=open('$ROOT/decoded/firmware/FTDX10_DISPLAY_V0106.bin','rb').read()
import re
for m in re.finditer(rb'[ -~]{8,}', d[0x32cbe0:0x32d280]):
    print(hex(0x32cbe0+m.start()), m.group().decode())"
```

结论：**在可见镜像范围内，升级/保底逻辑位于 DISPLAY 侧**；只刷 MAIN（不刷 DISPLAY）可保留出厂 boot loader 恢复通道。
（详见 `固件升级.md`。）
