# FTDX10 固件升级逻辑

> 对象：`decoded/firmware/FTDX10_MAIN_V0115.bin`（H8SX/1645，259,668 B）、`decoded/firmware/FTDX10_DISPLAY_V0106.bin`（ARM，3,373,532 B）、五个 `.SFL`、`decoded/firmware/*.srec`/`.rawhex`。
> 结论全部来自**二进制内容/指令**，不是据名字猜测。MAIN 地址给“文件偏移”；DISPLAY 若给“运行时地址”，会明确标注，其文件偏移 = 运行时地址 − `0x20100000`。
> 文中 `I:\...` 是固件里出现的 Windows 设备路径字符串，用于说明升级流程；它们不是本机路径，也不在本仓库中。

---

## 0. 一页结论

| 问题 | 结论 |
|---|---|
| 代码里有固件升级逻辑吗？ | **在可见镜像中，升级逻辑位于 DISPLAY（ARM）**，而且分两层：**①应用菜单层**（SOFT VERSION 界面/文件列表/校验）；**②独立 BOOT LOADER 层**（"FIRMWARE BOOT ERROR"→"INSERT FIRMWARE SD CARD."→"MAIN/DISPLAY FIRMWARE UPDATE"）。在可见 MAIN 镜像（`0x0–0x3F653`）中未发现升级/自编程逻辑；镜像外高位空间无法判断。 |
| 升级要完整固件还是"打补丁的 S-Record"？ | **必须完整固件**。SFL 载荷就是整片镜像：MAIN/AFCPU 为完整 S-Record 文本，DISPLAY/IFDSP 为裸二进制，SDR 为 hex 文本；引导器按"整文件"做 CRC32 校验 + 整段解码，头里 `<SIZE>`=整文件字节数、`<CRC32>`=整段密文的 CRC32。**只含改动记录的小 S-Record 不是受支持的输入**。 |
| 刷坏开不了机怎么恢复？ | **内置 BOOT LOADER**就是保底工具：开不了机会显示 `FIRMWARE BOOT ERROR` → 插 SD 卡按提示重刷（`MAIN FIRMWARE UPDATE` STEP 1/2、`DISPLAY FIRMWARE UPDATE` STEP 2/2），还有 `FORMAT SD CARD`、`REMOVE SD CARD.`。工厂级还有 `I:\AH068_DISPLAY_Loader.bin`、`I:\rom_writer.dat`（**不在公开升级包里**）。 |
| 最安全策略 | **只刷 MAIN，不刷 DISPLAY**。引导器在 DISPLAY 侧；不刷 DISPLAY 时通常仍可通过内置 Boot Loader 恢复。若 DISPLAY/Boot Loader 本身损坏，则无法依靠该通道。 |

---

## 1. 升级逻辑在哪：DISPLAY 里的两层

### 1.1 第一层：应用菜单（SOFT VERSION 界面）
DISPLAY 固件里的字符串与代码证据（地址为文件偏移）：

| 地址 | 字符串 | 作用 |
|---|---|---|
| `0x319AF` | ` YAESU FTDX10 FIRMWARE UPDATE` | 升级/版本界面标题 |
| `0xD484/94/A8/B8/C8` | `FTDX10_MAIN_V` / `_DISPLAY_V` / `_IFDSP_V` / `_SDR_V` / `_AFCPU_V` | 它按这 5 个前缀去找 SD 卡里的固件 |
| `0xD47C` | `.sfl` | 扩展名过滤 |
| `0xD4D8` | `File checking` | 文件校验中 |
| `0xD6F4` / `0xD70C` | `(Broken file)` / `(No such file)` | 校验失败 / 找不到文件 |
| `0xD704` / `0xD7E4` / `0xD7F0` | `Ready` / `Finished` / `failed` | 状态（对应手册里的 "Ready"） |
| `0xD45F/68/70/74` | `MAIN` / `DISPLAY` / `DSP` / `SDR` | 目标类别名 |

### 1.2 第二层：DISPLAY 中的独立 BOOT LOADER
`0x32CBE4`–`0x32D26C` 一整块引导器画面文本（紧邻 43 字节 SFL 密钥）：

```
alive                       FIRMWARE BOOT ERROR
YAESU FTDX10 BOOT LOADER V01-00
[ OK ]   [ NG : %s ]   [ OK ] %s
MAIN FIRMWARE FILE         DISPLAY FIRMWARE FILE
STEP 1 of 2.               STEP 2 of 2.
UPDATE?      DONE          LOADING  PROCESSING  SAVING
FORMAT SD CARD             Searching files...
UPDATE ERROR               SYSTEM WILL REBOOT
INSERT FIRMWARE SD CARD.   INSERT 'LATEST VERSION' FIRMWARE SD CARD.   REMOVE SD CARD.
TOUCH THE SCREEN TO CONTINUE.
MAIN FIRMWARE UPDATE       DISPLAY FIRMWARE UPDATE
DO NOT TURN OFF POWER      FIRMWARE VERSION ERROR
```

代码侧已定位（运行时地址；已按字面量池逐一核对，勿凭表序推断——同一函数内多条 `ldr` 共享一个字面量池）：
* `0x20156894` → `alive`（字面量 `0x2042CBE4`，同池还有 `testmode`）
* `0x201585B0` → `FIRMWARE BOOT ERROR`（`0x2042CBF6`）
* `0x20158604` → `UPDATE ERROR`（`0x2042CE60`）
* `0x2015874C` → `YAESU FTDX10 BOOT LOADER V01-00`（`0x2042CC0A`）
* `0x20158A4C` → `MAIN FIRMWARE FILE`（`0x2042CC3D`）
* `0x20158BF8` → `STEP 1 of 2.`（`0x2042CC70`）
* `0x2015A6A8` → `UPDATE?`（`0x2042CD28`）
* `0x2015BCC4` → `DONE`（`0x2042CD30`）
* `0x2015E438` / `0x2015E44C` → `I:\AH076H_DISPLAY.bin`（`0x2042CD52`）/ `I:\AH068_DISPLAY_Loader.bin`（`0x2042CD68`）
* `0x20160624` → `FORMAT SD CARD`（`0x2042CDEC`）
（均为 ARM `ldr rX,[pc,#imm]` + 字面量。）
* `0x2015E438` 那段的逻辑：把路径放进栈上缓冲，若模式变量 `==1` 就换成 `I:\AH068_DISPLAY_Loader.bin`，随后调用文件加载函数 —— 即**引导器可以从 SD 根目录加载"引导器本体/显示固件本体"文件**。

### 1.3 内部上传/加载通道（说明"分片喂给目标芯片"这件事确实存在）
`dsp1up` `dsp2up` `dsp3up` `dsp1up/32` `dsp1up/9` `dsp1up/32/9` `sdrup` `sdr1up` `sdr2up` `sdrchk1` `sdrchk2` `sdrfile` `fw1up` `fw1chk` `up0` `up1` `up2` `dspup` `fwupdate`
⇒ 对无 flash 或需在线加载的单元（DSP/SDR），固件是**上传**形式；对 MAIN/DISPLAY 是**写 flash** 形式。

## 2. SFL 混淆与校验（与我们的补丁直接相关）

| 地址(文件偏移) | 内容 | 说明 |
|---|---|---|
| `0x9B0` | CRC-16 表生成（`movw r3,#0xa001`） | CRC-16/MODBUS |
| `0xA34` | CRC-32 表生成（`ldr r3,[pc,#0x70] @0xAB4` = `0xEDB88320`） | 标准反射 CRC-32 |
| `0xA7C` | `crc32_update(ptr,len)` | 逐字节表查 |
| `0xAA8` | `mvn r0,r0` | **取反 ⇒ zlib 风格 CRC32** |
| `0xFBA8` / `0x10164` / `0x14CA0` | `A6 EC 9E 13` | SFL 头 `<CRC32>` 的固定尾部常量（3 个调用点） |
| `0x32D420` | 43 字节 SFL 密钥（`1E 27 1B 12 … 23 26`） | 完整密钥；被 `0x244`、`0x14C9C`、`0x15C3C`、`0x15C44` 四处引用 |

**整文件校验流程（反汇编实测，`0x14C60`–`0x14C94`）**：

```
14c70: bl 0x20100a7c        ; crc32_update(块指针, 块长度)   ← 循环分块读整个数据段
14c78: b  0x20114c48        ; 继续下一块
14c88: bl 0x20100a7c        ; crc32_update(..., 4)          ← 再喂 4 字节（尾部常量 A6 EC 9E 13）
14c8c: mvn r0, r0           ; 取反 = zlib CRC32
14c94: pop {r4,r5,pc}
```
⇒ 引导器/应用计算的就是 **CRC32(密文数据段 ‖ A6 EC 9E 13)**，**与我们重打包脚本用的算法完全一致**。

**基址判定**：`运行地址 = 文件偏移 + 0x20100000`。
证据：本节列出的 27 条引导器字符串中有 18 条的运行地址能以该基址在镜像里找到对应 32 位字面量（其余 9 条为拼接/间接引用）；且初始 SP 字面量 `0x2044C000` 恰好在 FLASH 末端（`0x20100000 + 0x3379DC = 0x204379DC`，bin 实际长度 3,373,532 B）之后，属 RAM。二者互相印证。

## 3. "需要完整固件"还是"打补丁的 S-Record"

### 3.1 SFL 的结构（决定必须是整片）

```
偏移 0..575   576 字节  文本头（9 行 CRLF）：[FILE NAME]/[PRODUCT NAME]/[FIRM VERSION]/[DATE]/COPYRIGHT
偏移 576..末  其余     混淆数据段（存储态密文；= 明文镜像，逐字节减去 43 字节循环密钥）
                        明文格式随 TYPE 不同：MAIN/AFCPU=S-Record 文本，DISPLAY/IFDSP=裸二进制，SDR=hex 文本
第 9 行        <TYPE> <SIZE> <CRC32>
```
五个包的 `<TYPE>/<SIZE>/<CRC32>`：

| 包 | TYPE | SIZE | 原厂 CRC32 |
|---|---|---|---|
| MAIN | `MC` | 738,986 | `DEE1F62A` |
| DISPLAY | `PC` | 3,374,108 | `8B764DC9` |
| SDR | `SR` | 4,392,794 | `77AC2625` |
| IFDSP | `ID` | 139,036 | `695023C7` |
| AFCPU | `AD` | 248,734 | `917F68A5` |

* `<SIZE>` = **整个 SFL 文件字节数**（含 576 头）。
* `<CRC32>` = CRC32(整段密文 ‖ `A6 EC 9E 13`)，见 §2。
* 明文 = **完整镜像**（不是差分包）；以 MAIN 为例是 S-Record 文本，覆盖 `0x0–0x3F653`（含复位向量与映像尾部版本串），即整片用户 MAT。

### 3.2 结论

* 引导器/应用对文件做的是**整文件级**校验（CRC32 覆盖整段密文、`<SIZE>` 必须等于整文件大小）与**整段解码**（43 字节密钥从数据段第一个字节开始按位置循环）。
* 写入是**整片作业**：MAIN 不能自编程 ⇒ 由外部写入器按 MAT 级写入；且 SFL 明文覆盖整片（含 `0x0` 复位向量），说明这是"完整镜像"语义，不是差分包。
* ⇒ **不能用"只含改动记录的小 S-Record"**：它既不是受支持的输入（头 SIZE/CRC 语义就是整文件），写出来的 flash 也会是不完整的。

| 项目 | 原厂 | 补丁 | 判定 |
|---|---|---|---|
| `[FILE NAME]` | `FTDX10_MAIN_V0115.SFL` | 同 | ✅ |
| `[FIRM VERSION]` | `V01-15` | 同 | ✅ |
| `[DATE]` | `2024/02/16` | 同 | ✅ |
| `<TYPE>` | `MC` | `MC` | ✅ |
| `<SIZE>` | 738,986 | **738,986**（字节数未变） | ✅ |
| `<CRC32>` | `DEE1F62A` | `3FED03DD`（按算法重算） | ✅ |
| S-Record 数据记录 | 16,230 | 16,230 | ✅ |
| S-Record 校验和 | 全合法 | 全合法 | ✅ |
| 明文差异 | — | **仅 5 字节**（`0x8112/0x1595C/0x159D4/0x3BB8A/0x3BCA6`） | ✅ |

## 4. 保底（砖机）恢复手段

### 4.1 现成的：内置 BOOT LOADER
* 触发画面：`FIRMWARE BOOT ERROR`。
* 提示：`INSERT FIRMWARE SD CARD.` / `INSERT 'LATEST VERSION' FIRMWARE SD CARD.` / `TOUCH THE SCREEN TO CONTINUE.` / `DO NOT TURN OFF POWER`。
* 流程：`MAIN FIRMWARE FILE` → `STEP 1 of 2.` → `DISPLAY FIRMWARE FILE` → `STEP 2 of 2.`；每步 `[ OK ]` 或 `[ NG : %s ]`；结束后 `SYSTEM WILL REBOOT`；出错 `UPDATE ERROR`。
* 其它功能：`FORMAT SD CARD`（卡坏了也能救）、`REMOVE SD CARD.`、`Searching files...`、`UPDATE?`、`DONE`。

### 4.2 工厂/维修级（**公开升级包里没有**）
| 路径 | 推测用途 |
|---|---|
| `I:\AH068_DISPLAY_Loader.bin` | **DISPLAY 引导器本体**（引导器自愈/重装） |
| `I:\AH076H_DISPLAY.bin` | DISPLAY 固件本体（非 SFL 形式） |
| `I:\rom_writer.dat` | "写 ROM"程序（工厂刷写） |
| `I:\AH076H_IFDSP.dat` / `I:\AH068_AFDSP_V0000.dat` / `I:\SDR00.hex` | IFDSP/AFCPU/SDR 的工厂文件 |

⇒ 真正"救不回"的边界是：**DISPLAY 及其引导器同时损坏**（此时需要 Yaesu 维修/这些工厂文件）。

## 5. 实操：刷机 / 回滚 / 砖机处置

### 5.1 常规刷机（同官方流程）
1. SD 卡由 FTDX10 本体格式化；把文件放到 **SD 卡 `FTDX10` 文件夹内**（与 `Capture`/`MemList`/`Menu` 同级），文件名必须 `FTDX10_MAIN_V0115.SFL`。
2. **只放 MAIN 一个文件**（本方案不需要动其它 4 个）。
3. 菜单 `EXTENSION SETTING → SOFT VERSION` → 勾选 → `UPDATE` → 中途不断电。

### 5.2 回滚（最常用）
* 把**原厂** `FTDX10_MAIN_V0115.SFL` 放回同一位置，重做 5.1 即可。

### 5.3 如果开不了机（砖机）
1. 关机 → 插入含**原厂** `FTDX10_MAIN_V0115.SFL` 的 SD 卡（同样放在 `FTDX10` 文件夹内）→ 开机。
2. 若出现 `FIRMWARE BOOT ERROR` / `INSERT FIRMWARE SD CARD.` → 按屏提示（`TOUCH THE SCREEN TO CONTINUE.`）让它执行 `MAIN FIRMWARE UPDATE`；不要断电。
3. 出现 `UPDATE ERROR` 就重来；出现 `FORMAT SD CARD` 提示就先格式化卡再重来；`SYSTEM WILL REBOOT` 即完成。
4. 若卡在 `FIRMWARE VERSION ERROR` / `INSERT 'LATEST VERSION' …`：说明引导器要求**不比当前低**的版本；此时用"版本号更高的重打包件"（见 5.4）。
5. 若连引导器画面都不出现 → 属 DISPLAY/引导器级故障，需 Yaesu 维修（或 `AH068_DISPLAY_Loader.bin`，非公开）。

### 5.4 版本号保险方案（可选，需要时可另行生成）
* 若引导器对"同版本"挑剔，可用备用件：把 SFL 头 `[FIRM VERSION] : V01-15` 改成 `V01-16`（头 CRC32 只覆盖数据段，改头不影响校验）；
* 更彻底：同时把 MAIN 镜像内版本串（文件偏移 `0x3F63E` 起的 `V01-152024-02-16-1`）同步改成 `V01-16…` 再重打包（会多改几个字节，仍属"完整固件"）。

## 6. 未决 / 说明

1. 引导器如何把数据写进 MAIN（直接驱动 H8SX boot/user-boot 模式，还是先下载小写到 RAM）——**从 MAIN 镜像无法判定**，但从可见镜像中未发现接收/自写逻辑，可判断写入不依赖 MAIN 应用。
2. `FIRMWARE VERSION ERROR` 的精确比较规则（是否允许等版本）未逐条反汇编确认；故给出 5.4 的版本保险方案。
3. `I:\rom_writer.dat` 等工厂文件的格式/用途未解析（公开包内不存在，无法获取）。
4. 行为差异：`INSERT 'LATEST VERSION' …` 与 `INSERT …` 两个提示的分支条件未逐条确认。
